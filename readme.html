!depende

Koncepcja lokalnego centrum utrzymania zależności, raportowania przeterminowanych pakietów, testowania projektów i kontrolowanego deployu na produkcję.

Streszczenie

!depende powstało jako praktyczna odpowiedź na pytanie: jak utrzymywać wiele projektów bez codziennego ręcznego sprawdzania zależności, podatności, lockfile, testów i produkcyjnych ścieżek deployu.

W katalogu znajdują się skrypty i raporty, które razem tworzą prosty system operacyjny dla maintenera: najpierw inwentaryzacja, potem raport HTML, potem konfiguracja projektów i zdalnych ścieżek, a na końcu orkiestrator, który potrafi instalować zależności, aktualizować je, uruchamiać testy, budować assety i opcjonalnie deployować.

Jak doszliśmy do tej koncepcji

1. Punkt startowy: chaos wielu repozytoriów

Pierwsze pytanie dotyczyło praktyki utrzymywania kilkudziesięciu projektów. Zamiast zgadywać, wykonaliśmy lokalną inwentaryzację manifestów: package.json, composer.json, requirements.txt, pyproject.toml i lockfile.

2. Raport zrozumiały dla człowieka

Surowy JSON okazał się za mało czytelny. Dlatego powstał raport HTML opisujący znaczenie liczb, różnicę między manifestem i lockfile, stan przeterminowania oraz ograniczenia audytu.

3. Orkiestrator utrzymania

Następnie powstał skrypt Python, który porządkuje powtarzalny proces: instalacja albo aktualizacja zależności, testy, build, opcjonalny deploy przez rsync po SSH.

4. Zdalne ścieżki produkcyjne

Po połączeniu z hostem SSH przeanalizowaliśmy katalogi zdalne, aplikacyjne .env, APP_NAME, APP_URL, DB_DATABASE i istniejące ścieżki WordPress/plugin/theme. Config dostał pola jakości dopasowania: remote_path_confidence, remote_path_source, remote_path_exists.

5. Wersje edukacyjne i anonimowe

Na końcu powstały anonimowe wersje skryptu z komentarzami dla laików: źródłowa, angielska i polska. Są bez realnych hostów, domen i ścieżek, więc nadają się do pokazania lub wrzucenia do repo jako przykład.

Co to daje użytkownikowi

  • Jedno miejsce kontroli: zamiast pamiętać o każdym projekcie osobno, użytkownik ma jeden katalog z raportami, configiem i skryptami.
  • Widoczność stanu zależności: raport pokazuje, gdzie są manifesty, lockfile, przeterminowane pakiety i braki danych.
  • Rozróżnienie ryzyka: system odróżnia projekty z potwierdzonym zdalnym katalogiem od zgadywanych albo nieznanych ścieżek.
  • Bezpieczny start: domyślnie skrypt działa jako dry-run i tylko wypisuje komendy.
  • Powtarzalny proces: update/install, testy, build i deploy są opisane w configu, a nie w pamięci maintenera.
  • Materiał edukacyjny: wersje _en.py i _pl.py tłumaczą kod linia po linii.

Co trzeba zmienić przed użyciem w innym repo

Najważniejsza zasada: nie używaj realnego prot-maintenance.config.json jako publicznego przykładu. Do repo nadaje się prot-maintenance.anonymized.example.json.

1. SSH

W configu ustaw dane serwera:

{
  "ssh": {
    "host": "deploy.example.com",
    "port": 22,
    "user": "deploy_user",
    "identity_file": "~/.ssh/id_ed25519"
  }
}

2. Projekty

Dla każdego projektu ustaw:

  • name - stabilna nazwa projektu do logów i --only.
  • path - lokalna ścieżka katalogu projektu.
  • enabled - czy skrypt ma go brać pod uwagę.
  • deploy - czy projekt wolno uploadować po podaniu --deploy.
  • remote_path - zdalna ścieżka deployu.
  • test_commands - komendy testowe, które muszą przejść.
  • build_commands - komendy buildu.
  • remote_commands - komendy wykonywane po deployu na serwerze.
  • excludes - pliki/katalogi niewysyłane przez rsync.

3. Deploy

Deploy wymaga trzech rzeczy naraz:

  1. uruchomienia z --execute,
  2. uruchomienia z --deploy,
  3. "deploy": true w konkretnym projekcie.

To celowe zabezpieczenie przed przypadkowym uploadem.

Jak to zbudować od zera

1. Wygeneruj config

python3 prot_maintenance.py --init-config --root /workspace --config maintenance.config.json

2. Uzupełnij config

Włącz projekty, ustaw zdalne ścieżki i dopasuj komendy test/build/deploy.

3. Zrób suchy przebieg

python3 prot_maintenance.py --config maintenance.config.json

4. Uruchom instalację z lockfile i testy

python3 prot_maintenance.py --execute --config maintenance.config.json

5. Uruchom aktualizacje zależności

python3 prot_maintenance.py --execute --apply-updates --config maintenance.config.json

6. Deploy tylko po weryfikacji

python3 prot_maintenance.py --execute --apply-updates --deploy --config maintenance.config.json

7. Jeden projekt przez filtr

python3 prot_maintenance.py --execute --only example-backend --config maintenance.config.json

Bezpieczeństwo i ograniczenia

rsync --delete jest mocne. Jeśli remote_path wskazuje zły katalog, można usunąć pliki produkcyjne. Deploy powinien być włączany tylko dla ścieżek ręcznie sprawdzonych.

  • composer update i npm update mogą zmienić lockfile.
  • Python w tej wersji nie ma pełnego modelu lockfile, więc wymaga ostrożności.
  • Raport outdated mówi o przeterminowaniu, nie o pełnej kompatybilności aktualizacji.
  • Testy są tak dobre, jak komendy wpisane w configu.
  • Wersje anonimowe są materiałem edukacyjnym; realny config powinien pozostać prywatny.

Jakie informacje warto dodać w repo

  • listę aktywnie utrzymywanych projektów,
  • politykę aktualizacji zależności, np. tygodniowo dla patch/minor, ręcznie dla major,
  • standard testów wymaganych przed deployem,
  • opis środowisk: local, staging, production,
  • regułę, że realne configi i raporty produkcyjne nie trafiają do publicznego repo,
  • checklistę review przed ustawieniem deploy=true.

Rekomendowany pakiet do repo

Do publicznego albo półpublicznego repo najlepiej dodać:

  • readme.html
  • prot_maintenance_anon_commented_en.py
  • prot_maintenance_anon_commented_pl.py
  • prot-maintenance.anonymized.example.json

Do prywatnego repo operacyjnego można dodać także realny skrypt i config, ale tylko jeśli repo jest zabezpieczone i nie zawiera sekretów typu hasła, tokeny, prywatne klucze ani produkcyjne wartości .env.

Minimalna checklista przed realnym deployem

  1. Sprawdź, czy remote_path_exists jest true.
  2. Sprawdź, czy remote_path_confidence jest high.
  3. Ręcznie obejrzyj zdalny katalog przez SSH.
  4. Uruchom skrypt bez --execute.
  5. Uruchom testy tylko dla jednego projektu przez --only.
  6. Włącz deploy=true tylko dla tego projektu.
  7. Dopiero wtedy uruchom --execute --deploy.
